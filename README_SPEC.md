# README 编写规范

本规范约束本项目架构与代码说明文档的编写方式。文档应使读者先理解 Agent 的整体运行流程，再沿目录层级和调用链逐步了解每个节点、函数及其数据流转。

本规范保存在项目根目录 `README_SPEC.md`；按本规范编写的文档统一输出到根目录下的 `README/`。根目录已有的 `README.md` 继续作为项目使用入口。

## 1. 核心要求

1. **按 Agent 架构分层。** 文档层级对应实际的 Agent、节点、工具、状态协议、Prompt、记忆服务及基础设施等职责，保持与源码结构的可追溯关系。
2. **以调用链作为叶子文档的主体。** 先给出完整流程，再按调用顺序逐步展开函数；每一步都说明输入、功能、输出及后续去向。不得用按字母排序的函数清单替代调用链说明。
3. **父目录负责抽象，叶子目录负责细节。** 父目录 README 介绍当前目录有哪些节点或子目录、分别实现什么功能、如何协作，不展开函数签名、参数表或实现细节。
4. **输入输出必须具体。** 不得仅写“输入为 state”“输出为 dict”；必须写明实际读取和更新的字段、类型、来源、条件及含义。
5. **以当前实现为准。** 以实际注册的图节点、边、条件路由及函数体为依据，不能仅依据文件名、旧注释或设计文档推断。尚未实现的内容必须明确标注，不能混入当前调用链。

## 2. 输出目录与层级

### 2.1 路径规则

- 所有生成的架构说明统一放在 `README/`，各级入口文件统一命名为 `README.md`。
- 每个纳入文档的目录都必须有 README；从总览到叶子，所有中间目录都必须有可导航的说明。
- 原则上镜像源码目录；需要详细说明的源码模块使用不带扩展名的同名目录承载叶子 README。例如 `agent/node/draft.py` 对应 `README/agent/node/draft/README.md`。
- 一个文件实现多个相关图节点时，在同一叶子 README 中按入口和调用链分节，明确每个图节点对应的函数。不要为了每个函数单独建立目录。
- 同一函数通过不同参数实例化为多个节点时，必须说明每个实例的差异。例如 `participant_state_in` 与 `participant_state_out` 共享工厂，但触发参数不同。
- 工具函数、后台任务、Prompt 和状态协议属于支撑模块，不应全部称为“图节点”；用目录职责和类型明确区分。
- 如需新增节点类别目录，必须有稳定的职责边界，且在父 README 中列明源码映射。仅为展示执行阶段时，优先在父 README 的表格中分组，不移动源码、不重复建立同一节点的文档。
- 历史设计或方案文档在内容并入对应分层 README 后移除，避免与当前实现重复；仅上游第三方参考资料（如 LangGraph checkpointer 说明）可作为附录保留，并在总览中标注其适用范围。设计方案不能替代基于当前代码的 README。

### 2.3 各级 README 的信息边界

| 层级 | 典型路径 | 必须说明 | 不在本层展开 |
| --- | --- | --- | --- |
| 系统总览 | `README/README.md` | 系统目标、入口、各子系统主要内容、端到端流程、阅读导航 | 具体函数的签名、参数和返回值 |
| Agent 总览 | `README/agent/README.md` | 图的生命周期、模块分工、状态与持久化边界、模块间协作 | 单个节点的内部实现 |
| 类别或父目录 | `README/agent/node/README.md` | 当前有哪些节点或子目录、各自功能、节点之间的关系与整体流程 | 子节点的逐函数说明 |
| 叶子模块或节点 | `README/agent/node/draft/README.md` | 入口、调用链、链中函数的输入输出与功能、路由和异常处理 | 无关模块的重复实现说明 |

层级深度不固定：只要目录下还管理其他文档目录，其 README 就必须承担抽象导航职责；具体函数说明下沉到相应叶子。

## 3. 父目录 README 规范

每一级父目录 README 必须包含以下内容：

1. **职责与边界**：用简洁文字说明当前目录实现什么能力、在上一层架构中处于什么位置。
2. **子目录或节点清单**：逐项列出名称、类型、主要功能、源码位置和下级文档链接。节点类别目录必须覆盖当前类别的全部已注册节点，并标注路由、共享实现或有条件启用的节点。
3. **整体协作流程**：用流程图或有序链路说明子模块如何衔接，展示关键分支和后台任务边界，只写模块或节点级功能。
4. **主要数据与依赖**：抽象说明上下文、候选回复、正式回复、记忆任务等如何跨模块流转，以及使用哪些外部服务；不列完整字段表。
5. **阅读导航**：提供返回上级及进入各子目录的相对链接。已有专题文档可作为补充阅读链接。

对于不承载执行流程的目录（如 `classes/`、`prompts/`），用“定义或注册 → 使用方 → 所支撑的功能”表达协作关系，不虚构运行调用链。

推荐清单格式：

| 节点或子目录 | 类型 | 主要功能 | 上下游或使用方 | 源码位置 | 详细文档 |
| --- | --- | --- | --- | --- | --- |
| `<名称>` | `<图节点/路由/服务/协议等>` | `<职责概述>` | `<协作关系>` | `<源码链接>` | `<下级 README 链接>` |

父目录可以使用实际图节点名表达流程，但不得继续展开对应函数的参数、返回结构或内部辅助函数。

## 4. 叶子 README：以调用链为主体

### 4.1 节点身份与入口

首先明确：

- 所属类别、职责、源码文件、图中的注册名称；不是图节点的模块标注实际类型。
- 上游来源、下游去向、触发时机和调用方式（同步、异步、框架调度或后台任务）。
- 工厂函数、工厂返回的执行函数和路由函数各是什么。内部同名函数使用限定名，例如 `create_draft_node.<locals>.node`。
- 同一模块存在多个入口时，逐项列出，并为每个入口提供对应链路；共享流程可以链接到同页的统一说明。

### 4.2 先给出调用链全貌

至少区分以下关系，避免将所有箭头都解释成直接函数调用：

| 关系 | 文档中必须表达的含义 |
| --- | --- |
| 构建关系 | 工厂初始化依赖并返回可调用对象，此时与运行时的入参不同 |
| 图调度关系 | 框架根据普通边或条件边执行下一节点；前一函数未必直接调用后一函数 |
| 函数调用关系 | 当前函数实际调用的函数、方法、工具或外部接口，以及返回位置 |
| 异步任务关系 | 生产者入队后返回，由独立消费者执行；说明交接的数据与结果消费时机 |

使用 Mermaid 或纯文本均可，但必须标明分支条件、循环返回位置、提前返回和结束点。各步骤使用稳定编号（如 `B1` 表示构建阶段，`R1` 表示运行阶段），并在后文按编号展开。

例如，说明当前 Agent 的图调度时应依据 `agent/builder.py` 中的实际注册关系，识别 `world_state_update` 对应 `update_world_state`、`update_iter` 对应 `increment_iteration` 等命名差异。不能只照抄可能滞后的函数注释。

当前图的主流程及分支可作为核对起点，后续源码变更时须同步更新：

```text
begin_turn → apply_memory_results → limit_context → world_state_update
  → participant_state_in → draft

draft --draft_judge 返回 tools--> tools → draft
draft --draft_judge 返回 check--> check
draft --draft_judge 返回 reply_failed--> reply_failed → END

check --check_judge 返回 draft--> draft
check --check_judge 返回 commit_reply--> commit_reply
check --check_judge 返回 reply_failed--> reply_failed → END

commit_reply → participant_state_out → update_iter → tts
tts --event_judge 返回 True--> prepare_memory → enqueue_memory → END
tts --event_judge 返回 False--> END
```

这只是图调度关系。叶子文档仍须进一步说明节点内部的函数调用，以及路由返回上述结果的具体条件。`enqueue_memory` 到后台 Worker 的关系应另画为队列交接，不能画成同步执行完记忆处理才结束本轮。

### 4.3 按链路逐步展开函数

每个步骤必须就地包含下表内容，使读者沿调用顺序即可理解完整行为，不需要跳到文末查找分散的函数说明。

| 项目 | 必填内容 |
| --- | --- |
| 定位 | 步骤编号、函数限定名、源码链接、实际签名及同步/异步属性 |
| 调用上下文 | 由谁调用、何时调用、调用条件、当前属于构建阶段还是执行阶段 |
| 输入 | 每个参数的名称、类型、含义、来源、默认值或必填性、有效范围或前置条件 |
| 隐式输入 | 闭包捕获的依赖、配置、环境变量、数据库内容、模型或 Prompt；无则明确写无 |
| 功能 | 按执行顺序说明校验、转换、判断、调用和组合结果的实际逻辑，解释关键处理目的 |
| 内部调用 | 调用了哪些函数、传入什么、使用其什么返回值、调用顺序；与下级步骤编号或文档链接对应 |
| 返回输出 | 返回类型、每个字段的含义、各分支差异、空值或无返回情况，以及谁消费该结果 |
| 状态变化与副作用 | 返回的状态增量、原地修改、文件或数据库写入、队列投递、模型请求、音频输出等，分别说明 |
| 后续去向 | 返回上层函数、交给框架合并状态、进入路由、调度下一节点或结束 |
| 异常与边界 | 抛出或捕获的异常、重试和上限、超时、取消、降级、提前返回及失败后的状态；未处理则说明向上抛出 |

补充要求：

- **状态字段逐项说明。** 对 `AgentState`、字典或结构化对象，列出实际读取与写入的字段、缺失时的处理和业务含义；共享协议的完整定义链接到所属叶子文档。
- **区分参数默认值与字段缺省。** 函数签名默认值、配置默认值和 `state.get(...)` 的回退值分别说明，不能混为一谈。
- **区分返回值与最终状态。** 返回部分字典通常是状态增量，不能称为“完整 AgentState”；说明未返回字段及 reducer 的实际处理方式。消息追加、按 ID 替换和显式删除应分别说明。
- **区分工厂与执行函数。** 工厂输入的角色、模型、工具、仓储等依赖与执行函数读取的本轮 state 分开写；工厂返回可调用对象，不能将节点运行结果误写为工厂返回值。
- **区分条件与路由目标。** 对每个条件列出实际返回值和 `builder.py` 中对应的下一节点，包含默认分支和失败分支。
- **展开关键内部函数。** 属于本模块的公开函数、内部闭包、私有辅助函数，只要参与所述链路，都应在首次出现处说明输入、功能和输出；公共依赖链接到其权威文档，并在本链路说明实际参数和返回值的用途。
- **控制重复。** 多条路径调用同一函数时，完整说明只保留一份，其余位置链接到对应步骤，同时写明本次调用的参数或用途差异。
- **保持覆盖可核查。** 每个节点入口、工厂、路由及参与行为的内部函数均须有对应步骤。模块内未接入当前主链、仅备用或单独调用的函数另列入口链并标注状态，不把它们伪装成正在执行的步骤。
- **外部依赖到边界为止。** 对框架、第三方库或外部服务说明本项目的调用契约及错误处理，不递归展开第三方实现。
- **不要伪造类型和机制。** 源码未标注类型时可以说明推断依据，但不得将推断标成原始签名；重试、超时或恢复机制只有代码实际存在时才写为已有能力。

### 4.4 分支、循环与异步链路

主链之后必须补齐适用的非正常路径，且仍采用“条件 → 调用函数 → 输入与处理 → 输出 → 去向”的组织方式：

- 工具调用与回到模型生成的循环。
- 检查不通过后的修订循环，以及内容修订次数与单次接口重试次数的区别。
- 功能关闭、依赖缺失、无有效输入或无需执行时的跳过路径。
- 异常、超时、重试耗尽以及失败收尾路径。
- 后台任务的投递、领取、处理、结果保存和后续应用链，注明哪些发生在不同执行上下文或不同轮次。
- checkpoint 恢复、重复执行和幂等处理；如当前模块不负责此事，链接实际负责模块。

每条非主路径都必须有明确的终点或回接点。路由条件可以用表格补充，但不能省略链中被调用函数的契约。

### 4.5 数据示例与支撑模块

- 对关键输入、输出或状态增量提供精简示例，并标注其对应的步骤和分支；示例中的字段与当前实现保持一致。
- 示例只保留解释行为所需的数据，使用虚构角色、消息和占位标识，不写入密钥或真实用户内容。
- `classes/` 的叶子以“定义 → 构造或校验 → 生产方 → 消费方”为主线，补充字段语义和约束；有方法时按调用步骤展开。
- `prompts/` 的叶子以“注册或获取 → 参数填充 → 消费节点”为主线，说明输入变量、生成内容及用途，不必复制完整长提示词。
- 没有可执行函数的模块明确写明这一点，记录数据或配置的使用关系，不编造函数调用链。

## 6. 链接、依据与维护

- 文档之间使用相对链接；跨模块函数链接到其权威说明，源码链接必须能从当前 README 正确定位。
- 相对路径按文档的实际深度计算。例如 `README/agent/node/draft/README.md` 返回上级是 `../README.md`，定位源码是 `../../../../agent/node/draft.py`。
- 同页步骤使用稳定且唯一的标题或显式锚点，避免多个同名 `node` 造成引用不清。
- 行号仅作辅助定位，源码路径与函数限定名才是主要标识，避免代码移动后失去对应关系。
- 对源码中的注册表、条件分支、配置和已有测试进行交叉核对。区分静态阅读所得、已有测试覆盖和本次实际执行验证，不得虚报测试结果。
- 新增、删除、重命名节点或调整路由时，同步维护节点叶子 README、直属父目录清单以及受影响的上层流程；仅修改内部实现时，更新受影响的调用步骤及契约。
- 不再存在的节点应从当前清单和链路移除；若需保留历史方案，明确标记其历史性质并更新链接。
- 当前 `.gitignore` 忽略 `data/`，但不匹配根目录 `README/`，因此文档默认会进入版本控制；是否纳入版本控制单独决定，不因编写文档自动改动忽略规则。

- [ ] 本规范位于根目录；架构文档输出到 `README/`，各级入口统一为 `README.md`。
